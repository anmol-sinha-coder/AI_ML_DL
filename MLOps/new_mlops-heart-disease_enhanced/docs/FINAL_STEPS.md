# From working code to a finished submission - ordered runbook

Follow the steps in order. Every step lists the command, what "good" looks like, and which screenshot/evidence to take.
Time budget: about 2.5 h including the video. Run everything from the project root.

## Step 0 - Why Grafana showed "No data" (and the fix)

| # | Cause in the old files | Fix now in the project |
|---|---|---|
| 1 | `monitoring/prometheus.yml` contained a stray `apiVersion: 1` (Grafana syntax). Prometheus refuses to start with it ("field apiVersion not found"), so no data ever existed. | Clean Prometheus-only config; a unit test (`test/test_monitoring_config.py`) and CI (`promtool check config`) now fail if this happens again. |
| 2 | Datasource referenced by name only; no fixed `uid`; an older/manual "Prometheus" datasource with `localhost:9090` would not work from inside the Grafana container. | `provisioning/datasources/prometheus.yml`: uid `prometheus`, URL `http://prometheus:9090`, `deleteDatasources` removes stale copies. Dashboard panels use that uid. |
| 3 | Dashboard had 2 basic panels and relied on default metrics only. | 42 panels in 8 sections, generated by `monitoring/build_dashboard.py`; custom API metrics for predictions, risk bands, inference latency, input drift, model info. |
| 4 | Nothing proved that the queries match real metrics. | `scripts/verify_monitoring.py` runs every dashboard query against Prometheus and reports empty panels. |

If you keep your current stack running, the quickest repair is: delete line 4 of `prometheus.yml`, then
`docker compose restart prometheus`. For the full new dashboard follow the steps below.

## Step 1 - Clean slate and full deployment (≈10 min)

```bash
docker compose down -v 2>/dev/null; docker rm -f mlflow_server ml_api prometheus grafana 2>/dev/null
chmod +x initial_deploy.sh scripts/*.sh scripts/*.py
./initial_deploy.sh --reset            # add --helm or --k8s later (Step 6)
```

Good = the script ends with the "Stack deployed" banner **and** `verify_monitoring.py` printed
`RESULT: PASS`. It already started 3 minutes of background traffic.
Evidence: `scripts/capture_evidence.sh tests` and `scripts/capture_evidence.sh train`.

## Step 2 - Check each link of the monitoring chain (≈3 min)

```bash
curl -s localhost:8000/metrics | grep -E '^(heart_|http_requests_total)' | head      # 1. API exposes metrics
open http://localhost:9090/targets        # 2. job fastapi-ml-app must be UP (green)
python3 scripts/verify_monitoring.py      # 3. all dashboard queries have data; also checks Grafana datasource
```

Grafana: http://localhost:3000 (admin / admin; skip the password prompt) -> the home page already is the dashboard
"Heart Disease MLOps - Monitoring". Datasource check: Connections -> Data sources -> Prometheus -> *Save & test* = green.

## Step 3 - Generate traffic for the dashboards (≈4 min)

```bash
python3 scripts/generate_traffic.py                                   # demo profile, 3 min: ramp, spike, cool-down
python3 scripts/generate_traffic.py --profile steady --rps 15 --duration 120
python3 scripts/generate_traffic.py --profile spike --rps 20 --duration 90
python3 scripts/generate_traffic.py --url http://localhost:18080      # Kubernetes (port-forward, Step 6)
```

The mix is ~90 % valid patients (sampled from the real dataset), ~8 % invalid payloads (HTTP 422), a few 404s and
health checks - so the error, status-class and latency panels all show something. Keep it running while you take the
Grafana screenshots; the dashboard time range is the last 15 minutes with 10 s auto-refresh.

What to look at in Grafana (top to bottom): *Overview* (targets up, rate, error ratio, p95, predictions, high-risk
share, model loaded) - *Traffic* - *Latency* (percentiles + heatmap) - *Errors* - *Model behaviour* (predictions per
outcome, risk-band donut, P(disease) distribution) - *Input data monitoring* (mean age/chol/BP/heart-rate: drift watch) -
*Process resources* - *Deployments* (compose vs k8s scrape health). Use the **Deployment** and **Instance** drop-downs
at the top to compare compose with Kubernetes.

Prepare: browser at 1920x1080 zoom 100 %, terminal font 16 pt, hide personal tabs. Order:

```bash
python3 -m pip install playwright && playwright install chromium     # once
scripts/capture_evidence.sh docker        # text proofs (images, health, logs, predict)
```

Then terminal/GitHub shots by hand (`scripts/shot.sh 09_docker_ps_health --delay 5`) - see the table in
`screenshots/README.md` for the exact list and file names (18 items). If your system uses Wayland/GNOME the
first call may ask for permission; `sudo apt install gnome-screenshot` is the most reliable tool.

## Step 6 - Kubernetes: manifests, then Helm (≈15 min)

```bash
scripts/deploy_k8s.sh --manifests          # Deployment x2 + LoadBalancer Service on Minikube, smoke-tested
scripts/capture_evidence.sh k8s            # pods, svc, URL
scripts/deploy_k8s.sh --helm               # switches to the Helm release "heart-disease-api" (removes the manifest one)
scripts/deploy_k8s.sh --helm --ingress --hpa   # optional Ingress (heart.local) + autoscaling
helm list; helm status heart-disease-api   # screenshot 13
```

The script also registers the cluster as a Prometheus target (`monitoring/targets/k8s.json`, label
`deployment="k8s"`) and connects the Prometheus container to the `minikube` Docker network, so the same dashboard shows
the Kubernetes pods after ~30 s (Prometheus -> Targets: `fastapi-ml-app-k8s` UP). Drive traffic at it with
`kubectl port-forward svc/heart-disease-api 18080:80 &` and `generate_traffic.py --url http://localhost:18080`.
Teardown: `scripts/deploy_k8s.sh --teardown`.
Equivalent one-shot: `./initial_deploy.sh --helm` (or `--k8s`).

## Step 7 - GitHub repository and CI/CD (≈15 min)

> The Actions workflow only runs if `.github/workflows/` is in the **repository root**. If `mlops-heart-disease` is a
> sub-folder of a bigger repo (e.g. AI_ML_DL), either create a dedicated repo for this project (recommended) or move
> `.github/` to the root and add `defaults: run: working-directory: mlops-heart-disease` plus matching artifact paths.

```bash
cd mlops-heart-disease
git init -b main && git add . && git commit -m "MLOps heart disease pipeline"
git remote add origin https://github.com/<user>/mlops-heart-disease.git
git push -u origin main
```

Open the **Actions** tab: jobs `lint-test-train`, `validate-deploy-configs`, `docker-build-test` must be green; open one run
and capture (05) the green graph, (06) the *Artifacts* list (`ml-artifacts`, `docker-logs`, `helm-rendered`), and the job
summary with metrics. Put the repo URL into `README.md` ("Submission checklist").

## Step 8 - Prove the pipeline fails on errors (≈5 min)

```bash

git commit -am "demo: break lint" && git push -u origin demo/failing-ci
```

Open a pull request / the Actions run: red cross + clear log line `F401 'os' imported but unused` -> screenshot 07.
Then: `git checkout main && git branch -D demo/failing-ci && git push origin --delete demo/failing-ci`.
(For a failing *test*: change an expected value in `test/test_api.py`.)

## Troubleshooting "No data" in Grafana - in this order

1. `docker compose ps` - is `prometheus` **Up**? If it restarts: `docker compose logs prometheus | tail` (config error).
2. http://localhost:9090/targets - `fastapi-ml-app` UP? If DOWN: `docker compose logs api`; is the API healthy?
3. `curl localhost:8000/metrics | head` - metrics present? Did traffic run in the last 15 min?
4. Grafana: Connections -> Data sources -> Prometheus: URL must be `http://prometheus:9090` (not localhost) -> *Save & test*.
5. Old dashboard still shown ("ML Model Monitoring Dashboard")? It is a leftover - `docker compose down -v` (wipes Grafana's
   database) and start again, or open the new one: http://localhost:3000/d/heart-disease-api
6. Panels empty but Prometheus has data? Set the variables at the top to **All**, time range **Last 15 minutes**.
7. Still stuck: `python3 scripts/verify_monitoring.py` names every panel that has no data.
